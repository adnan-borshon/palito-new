# M4 healthcare implementation

M4 is a separate, real `/api/v1` workspace at `/care` in Next and Expo native. Existing role/demo screens still use their labeled local demo repository. No DemoState import, synthetic health score, invented clinical advice, payment receipt, video provider or background delivery is returned by the new API.

## Pilot choices

- Booking defaults **off**. Set `HEALTHCARE_NO_CHARGE_PILOT=true` explicitly in a development/staging API to allow BDT 0 appointments. Every successful booking returns `payment.mode=NO_CHARGE_PILOT`, canonical `amountMinor="0"`, `currency=BDT`. It does not create a payment or claim one was collected. Paid care waits for M6 and reviewed provider/policy integration.
- Server timestamps are UTC ISO strings ending in `Z`; slots must start on a whole minute, last exactly 30 minutes, and be within 90 days. Clients display appointment dates in **Asia/Dhaka (UTC+6)**. Availability editing takes explicit UTC instants; it does not silently interpret an ambiguous local timezone. Consultation may start 15 minutes before the booked start; access expires 72 hours after its end.
- Only verified, active vets with current active CLINIC membership and fresh password/email-verification/SMS-MFA context may publish slots or sign. Practice district/species/description are explicitly self-reported professional details, separate from credential verification. Directory filtering is by name, district and species; missing practice information is shown as missing.
- Booking consent `care-v1` authorizes the assigned vet to read this animal's passport, clinical history, current visit address and current-owner private files until 72 hours after the appointment ends. The farmer can withdraw immediately. Rejection/cancellation also revokes consent. Current ownership must still match the consenting farmer; transfer invalidates earlier grants and private-file links. Bank, insurer and administrator roles have no clinical bypass.
- `REQUESTED → ACCEPTED → IN_PROGRESS → COMPLETED`. The assigned vet can reject a request; participants can cancel REQUESTED/ACCEPTED. The current owner can reschedule those states to a future open slot of the same vet, requiring renewed explicit consent and vet acceptance. Withdrawn consent cannot be revived through rescheduling; cancel and create a new consenting booking. No cancellation/reschedule of completed/in-progress care.
- A signed clinical finding can be a checkup, vaccination or treatment. A vet supplies medicines/dose/frequency/days/advice and an optional explicit follow-up instant. No veterinary schedule or treatment is inferred. A signature is a server-associated verified prescriber and immutable database record, **not blockchain verification or a cryptographic document-signing claim**. Corrections append a linked amendment with a reason; they never overwrite the signed original. The original prescription stays signed and immutable.
- Reminder schedules and append-only care event intents commit with the corresponding domain write. M5 must add delivery jobs, deduplication/recovery and retention processing. Saved reminder does **not** mean an SMS/push/email was sent. No notification provider is called by M4.

## API contract

All routes require a current M3 identity. Cookie mutations require same-origin CSRF; native uses fresh SDK bearer proof. IDs are UUIDs; unknown/foreign scoped resources give safe 404. Validation rejects undeclared actor/owner/vet fields. Mutations require actor-bound `Idempotency-Key` (8–100 letters/digits/underscore/hyphen). Receipt operation, payload hash and resulting IDs commit atomically under a database advisory lock. Replaying a command rechecks current resource authority. Versioned changes additionally require `If-Match` as the current integer version; stale updates return 409. Retry a lost response with the **same key and payload**, then reload current versions.

| Routes | Input/result and scope |
|---|---|
| GET/POST `/farms`; PATCH `/farms/:id` | Owner-only; name, district, address, exact areaAcres decimal string. Edit requires version. |
| GET/POST `/animals`; PATCH `/animals/:id`; POST `/animals/:id/archive` | Owner-only. Registration: owned farmId, name, canonical cattle/goat/buffalo/sheep, breed, female/male/unknown, birthDate YYYY-MM-DD, weightKg decimal string, canonical estimateMinor poisha string, optional unique uppercase tag. Archive is soft, versioned, reasoned, denied while care is active. No ownership transfer API is exposed. |
| GET `/animals/:id/passport`, `/records`, `/files`; POST `/observations` | Current owner or consented verified vet reads. Owner creates observations, explicitly distinct from signed clinical records. Passport includes current visit location; history is paginated and exposes signed prescription references, amendments and provenance. File list contains IDs/purpose/time, never bytes or public URLs. |
| GET `/vets`, `/vets/:id`, `/vets/:id/slots` | Verified active directory/professional projection only. Optional directory `search`, `district`, `species`. No email, phone, identity-provider UID or membership identifiers. Future open slots only. |
| GET/PUT `/vets/me/availability`; PUT `/vets/me/profile` | Verified vet self; If-Match 0 for first write, then returned version. Availability `{startsAt: UTC[]}` replaces OPEN slots, preserving BOOKED slots. Profile `{district,species,bio}` is self-reported. |
| GET/POST `/appointments`; GET `/appointments/:id` | Owner/current consented participant only. Booking `{animalId,slotId,mode:visit|video,reason,consent:true,consentVersion:care-v1}` derives farmer/farm/vet/times server-side. Queue filtering occurs before pagination. `video` is a remote-care scheduling choice; vet coordinates the call. No call-token/provider success is fabricated. |
| POST `/appointments/:id/decision`, `/cancellation`, `/reschedule`, `/consent-withdrawal` | Assigned vet decision `{decision:accept|reject,note}`; participant cancellation `{reason}`; owner reschedule `{slotId,consent:true}`. Versioned except irreversible withdrawal. Idempotent repeated withdrawal is safe. |
| POST `/appointments/:id/consultations`; POST `/consultations/:id/completion` | Assigned verified vet, active consent, current version/state. Consultation ID is appointment ID, not a separately invented session. Completion `{kind?,diagnosis,advice,medicines:[{name,dose,frequency,days}],followUpAt?}` signs health record, prescription/items and event/reminder in one transaction. |
| GET `/prescriptions/:id`; POST `/records/:id/amendments` | Current patient scope; amendment requires original prescriber, current vet context and `{note,reason}`. Prescription items cannot be edited/appended/deleted after signing. |
| GET `/reminders`; PATCH `/reminders/:id` | Current owner/snapshot match; `{enabled}` with version. Delivery reports NOT_ENABLED_M5. |
| POST `/files/uploads`; PUT `/files/:id/content`; POST `/files/:id/completion`; GET `/files/:id`; GET `/files/:id/download` | See private-file protocol below. File info supports recovery after a lost binary-upload response. |

Farm/animal/vet/appointment/history/file lists use a stable `(createdAt,id)` opaque cursor and limit 1–100; reminders use `(dueAt,id)`. Clients traverse pages, with an explicit 1,000-row workspace limit instead of silently truncating. Public open-slot and self availability views are bounded to 100 entries (at most 64 new open slots per publication).

## Private file protocol and limits

1. Initialize `{animalId,purpose:animal-photo|clinical-evidence,contentType:image/png|image/jpeg,sizeBytes}` with a command key. The ID is bound to patient, current owner snapshot and uploader for 15 minutes. It is PENDING and cannot be downloaded.
2. PUT the exact PNG/JPEG bytes to returned uploadPath with current authorization (and CSRF for cookies), declared Content-Type and size ≤1 MiB. The server verifies decoding and actual format with pinned Sharp, bounds decoded pixels to 20 million, autorotates, strips metadata/GPS, bounds output to 2048 pixels and canonical PNG ≤4 MiB. HTML/undecodable images and wrong type/length are refused. Original bytes are not retained.
3. Server stores QUARANTINED canonical bytes and returns SHA-256. POST completion `{sha256}` before expiry under a durable key; only matching uploader/current patient scope may finalize. If the PUT response was lost, GET file metadata to recover the canonical hash and continue. READY bytes/identity are immutable by database trigger. Photo linkage requires the same animal/current owner and READY animal-photo purpose at API and database boundaries.
4. Downloads are authenticated streams with `no-store`, no-sniff, attachment filename and fresh current-patient authorization **on every fetch**. There is no bearer URL or public bucket. Withdrawal, expiry, credential/membership/account revocation and ownership change deny subsequent fetches. Previously viewed bytes cannot be recalled from a person's device.

M4 deliberately uses a private PostgreSQL byte-object pilot adapter; it is **not an S3 integration** and must not be described as production object storage. Canonical image limits are deliberately small. Select a managed private object store, quotas, retention/deletion and malware scanning for additional document formats before larger live rollout. M4 accepts only decoded/re-encoded PNG/JPEG, not PDF, video, office files, executables or arbitrary attachments. M5 owns expiry/retention job processing; abandoned records are not claimed as cleaned automatically.

Both clients keep private care views, pending command keys and images in memory. Native relies on official Firebase SDK identity persistence; care does not store tokens in AsyncStorage. Background/sign-out/account changes fence pending reads and clear care views. Web uses HttpOnly cookies, fresh CSRF and no local/sessionStorage care persistence. Returning to care requires a fresh load. Native image selection uses SDK-compatible Expo picker/file-system/crypto modules; no microphone/camera permission is requested. Live SDK/device acceptance remains the M3 release gate.
